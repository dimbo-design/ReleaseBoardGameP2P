# PR #134 — разбор и исправления по ревью dimbo-design

Проверено 2026-09-13 по [комментарию dimbo-design](https://github.com/MythHand/ReleaseBoardGameP2P/pull/134#issuecomment-5614396329).
Повторное чтение GitHub подтвердило, что новых текстовых замечаний автора нет.
Исправления находятся в `feat/108-git-cards` поверх `3f6a8b6`; два новых коммита
удалённой ветки включены, пересечения разрешены с сохранением обеих сторон.
Ответ подготовлен для публикации автором задачи в обсуждении PR. Ниже отдельно указаны исправления,
результаты проверок и оставшиеся ограничения.

## Часть 1 — Git-карты, пункты 1–8

1. **Cherry-pick: выбор нельзя передумать.** Повторный выбор заменяет прежний, а не блокирует
   остальные карты. Базовый браузерный путь с перевыбором и финальным прибытием в руку проверен.
   Отказ RESOLVE снимает блокировку; отказ автоматического ответа при единственном варианте
   открывает ручной повтор.
2. **Cherry-pick: взаимодействие и куча под гридом.** Пока грид владеет кандидатами, видимая куча
   и счётчик скрыты. Невыбранные карты возвращаются в кучу. Рецепт и аудит синхронизированы;
   полного визуального паритета по всем режимам пока не утверждаем.
3. **Cherry-pick: несколько конкурирующих анимаций.** Принятое `takenFromDiscard` запускает
   единственный handoff грида, а очередь ждёт его. Карта в руку, sudo-карта на колоду и возврат
   остальных завершаются совместно. Куча учитывает `takenFromDiscard`, поэтому выбранная карта
   не остаётся в ней. Позы возврата берутся из принятого after-heap и распределяются один к одному,
   в том числе между картами одного каталожного типа.
4. **Rebase: порядок и следующий добор.** Добавлена обработка отказа: ряд открывается снова и
   позволяет повторить ответ. Ветка выбора стопки сохраняет её индекс; перестановка использует
   общий `useCardReorder`. В браузере Database перемещена с третьей позиции на первую,
   и следующий добор из этой же стопки дал Database. Обе стопки sudo Rebase также переставлены
   и приняты. Тесты движка проверяют следующий добор, а сессионные тесты — передачу результата
   host/guest, даже когда принятый RESOLVE не создаёт событий. Ошибка обработки отказа подтверждена;
   установить, был ли в старом прогоне отказ или добор из другой стопки, без его журнала нельзя.
5. **Rebase: клавиатура.** Обработчик ArrowLeft/ArrowRight удалён с борда. Основное
   взаимодействие — общий drag; проверка порядка полёта переведена на pointer drag.
6. **System Upgrade: настоящий pull из руки.** Список выбора с подтверждением для взноса убран.
   Карта летит из фактического rect вытягивания в измеренный слот ряда шириной 150 px; RESOLVE
   отправляется после посадки. Принятый такт принимает носитель, отказ возвращает карту в веер.
   Места ряда резервируются до измерения. Финальный base-такт держит ряд 2500 мс и отправляет
   карты из этих же узлов в сброс через `useDiscardExit`, со стаггером 90 мс. Sudo-такт ведёт
   выбранную карту через центр в руку, остальные — из ряда в сброс. Дублирующий общий такт
   удалён. Инструкция о взносе видна; подтверждение нужно только актёру при sudo-выборе.
   Дополнительный тест reduced motion нашёл сохранённую блокировку после принятого взноса:
   следующий Upgrade не позволял вытянуть карту. Очистка исправлена; тест повторного Upgrade
   и сохранение обычного handoff проходят.
7. **Отклонения от сценариев не записаны.** Обновлены `recipes.md`, `backlog.md` и страница
   Interaction audit. Записаны реализованные движения и оставшиеся вопросы. Миграция общего
   фолда ещё не завершена: локальные реализации остаются в `_useBoardStaging` и `comboBeat`.
   Это документирование состояния, а не новое утверждение об одобрении визуального результата.
8. **Не было согласования на отладку анимаций борда.** Техническая правка не заменяет согласование.
   Этот черновик разделяет изменения реализации, наблюдения браузера и непроверенные сценарии.
   Общего апрува анимаций здесь не заявляем; возврат PR в draft и корректировка его описания
   перечислены отдельно ниже.

## Часть 2 — анимации стола, пункты 1–6

1. **Розыгрыш кликом.** Самостоятельный розыгрыш из руки начинается вытягиванием; клик его не
   запускает. Клики по целям/партнёру после staging остаются частью соответствующего выбора.
2. **Потерян центр.** Targetless Git и Monitoring сначала проходят `stagePlain`, затем
   отправляют действие. У карт с целью после staging остаётся выбор цели. Это описание
   исправленного пути, не утверждение о проверке каждой карты в браузере.
3. **Monitoring телепортируется.** Его pull проходит через центр до отправки действия;
   дальнейший beat получает staging для движения в зону релиза.
4. **AI-триггер уходит раньше эффекта.** `aiCause` остаётся рядом с эффектом на время pending;
   соответствующая карта исключается из видимой кучи и счётчика. При ответе причина уходит
   в сброс вместе с возвратом эффекта. Порядок банковки в движке не менялся и остаётся вопросом
   в backlog. В браузере Bad Vibe дождался реального вытягивания карты из руки: причина
   оставалась рядом, затем ушла в сброс, эффект вернулся в событийную колоду; pending завершён.
5. **Защита релиза.** Defense staging использует общий `usePairFold`; локальные биты защиты
   и нейтрализации ждут `whenLanded` перед `SHOW_HOLD`. Одиночная атака и атака с Sudo
   прилетают сразу в наклон pending; пара движется целиком, как в Defense Release.
   Проверены обычная защита и sudo Rollback локально и для удалённого игрока.
   Возвратная анимация Rollback/редирект Works on my Machine всё ещё зависят от отсутствующего
   `defended.parent` в движке — это исправление открытого #139, которое здесь не дублируется.
6. **Запоздалая тревога 503.** У стоящей 503 снят дополнительный `TABLE_HOLD` 2600 мс: после
   вскрытия и `AFTER_FLIP` управление переходит pending/тревоге. Холды уже сбанченных триггеров
   и чтения AI-эффекта не отменяются.

## Матрица проверок

Браузерный проход выполнен на настоящем `Board`, reducer и очереди анимаций, в локальном
детерминированном стенде с seed 42 и двумя игроками. Начальные руки/колоды фиксированы;
действия проходят через reducer, принятые события возвращаются в очередь. Это проверка
рендера и стыков анимаций, а не двух физических WebRTC-браузеров.

| Сценарий | Результат |
|---|---|
| Cherry-pick base | Перевыбор; принятая карта в руке; остальные вернулись в кучу |
| Cherry-pick sudo | Третье нажатие заменяет пару; Backend в руку, Database на колоду; грид закрыт |
| Rebase base | Drag третьей карты на первую позицию; следующий добор той же стопки — Database |
| Rebase sudo | Обе строки переставлены; ответ содержит и принимает оба порядка |
| Upgrade base | Взнос вытянут из настоящей руки; видимая подсказка; карта покинула руку, ряд ушёл в сброс |
| Upgrade sudo | Взнос соперника попал в ряд; выбранная карта через центр пришла в руку; pending закрыт |
| Cherry-pick без подходящих карт | В сбросе только триггер; карта операции потрачена, лишняя поверхность не открылась |
| Rebase с пустой стопкой | Операция завершилась без ряда и зависшего pending |
| Upgrade без чужих карт | Операция завершилась без запроса взносов |
| Monitoring | Вытягивание → центр → слот Monitoring; в руке копии не осталось |
| AI / Bad Vibe | AI-причина дождалась сброса; эффект вернулся в колоду; причина ушла в сброс |
| Error 503 | Красное свечение при pending; вытянутый Debugger завершил нейтрализацию и покинул руку |
| Defense Release | Hotfix локально, Rollback base/sudo у удалённого игрока, sudo Rollback локально: ответ принят, релиз сохранён |
| Sudo-атака | Пара прилетела с наклоном; пропуск защиты завершил pending и сбросил обе атакующие карты |

`prefers-reduced-motion` проверяется автоматическими тестами; отдельный браузерный проход
с настоящим media preference не выполнен. Это ограничение остаётся в матрице, а не скрывается
за успешными тестами. Полный визуальный апрув всех сцен не заявлен.

## Границы результата

- RESOLVE timing Cherry/Rebase остаётся записанным вопросом; оба существующих режима
  теперь обрабатывают отказ. Момент отправки не менялся ради унификации.
- Миграция оставшихся локальных реализаций образования пары и общее объявление поз
  остаются в аудите. Это не мешает исправленному прилёту sudo-атаки.
- #139 нужен для полного хвоста Rollback/Works on my Machine. При его интеграции общие
  блоки аудита и backlog должны сохранить и закрытие связи атака/защита, и новые Git-исправления.
- Draft/описание PR и решение об отдельном плане #104 — организационные пункты. Комментарий
  в PR не отправлялся, его статус и описание не менялись. Чужой план не удалён, история коммитов не переписана.
